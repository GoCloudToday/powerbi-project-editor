# Row-level security and access levels

Dynamic roles, roles that follow another model's user table, composite-model security, reading and changing the role members of published models. Rows moved verbatim from the v1 SKILL.md quick reference in v2.0.0; `§` references point to [reference.md](../reference.md). Where a row disagrees with the core, the row wins.

The core refuses role-membership changes. This overlay allows them only when the model owner explicitly asks: the model's Security page in the service first, the XMLA side effects stated (no PBIX download afterwards), no XMLA route on a model with Query Scale-Out (overrides in SKILL.md). That override takes precedence over the row below that goes straight to TOM.

| Situation | Rule |
|---|---|
| RLS that must follow another model's user-to-country table | Copy the table on every load (executeQueries as a workspace member), keep it as a hidden dual table filtered to the user's own rows, OR it into every country filter (GLOBAL row = all, plus the source's sub-domain rule); it opens rows to read only, the write list stays apart. Service "View as" banner "This user does not have access to the dataset or report." = item permission, not RLS. reference.md §2026-11-20 round 25. |
| Several access levels (per page, read-only) on one model | ONE role and typed access rows: the shared dimension filtered by the union of the page types, each page's fact tables by their own type only (no leak through totals), a read-only type that lifts every filter but passes no save check. Page slicers get a visual filter on a "show this key" measure that is also 1 with no rows at all (the author's Desktop sign-in has none). Test levels with temporary `@example.invalid` rows. reference.md §2026-10-23 round 2. |
| Reading RLS roles off a PUBLISHED model | `INFO.ROLES()`/`INFO.TABLEPERMISSIONS()` via REST `executeQueries` are BLOCKED (as is EVERY `INFO.*` function on some datasets - see the footprint row) (400, AS code 3239575574) though other INFO functions work; ADOMD/XMLA with an Azure-PowerShell Power BI token 401s despite a correct `aud`. Use the items API: `POST …/semanticModels/{id}/getDefinition?format=TMDL` → poll `Location` → `/result` (base64 TMDL incl. `roles/*.tmdl`). ADOMD needs PowerShell 5.1 (`CallContext` type-load error under 7). reference.md §2026-08-25. |
| "RLS users see less data than write users" | RLS on a dimension DELETES fact rows whose FK doesn't resolve — the unmatched row sits on the relationship's blank member, which every `tablePermission` excludes. Isolate by applying each role predicate alone via `TREATAS`. **Never** relax it to `… \|\| ISBLANK(bridge[key])`: measured, that leaked every other tenant's dangling rows into one tenant (9,639 → 1,683,563 rows). Fix by backfilling placeholder dimension rows carrying the tenant key — after verifying each dangling key maps to exactly ONE tenant. |
| Adding RLS role members to a PUBLISHED model by code | No REST API does it: TOM over the XMLA endpoint with an interactive sign-in (SSMS AMO in Windows PowerShell 5.1), one `ExternalModelRoleMember` per user or group (a group as `obj:<groupId>@<tenantId>`), one `SaveChanges`. Needs XMLA read-write and the model owner's explicit go (it grants data access). The members survive a later Desktop publish (Replace); prove it with the impersonation gate after each publish. reference.md §2026-10-23 round 2. |
| `executeQueries` reproducing an RLS identity | `impersonatedUserName` 401s with `RLSNotAuthorizedForModel` unless you own/administer the dataset — simulate the role with `TREATAS` instead (matched the real report output exactly). As the OWNER it works and tells role membership by effect (members can't be read via API): `RLSNotAuthorizedForModel` = the person is in NO role; a workspace Admin/Member/Contributor is NOT impersonated (the answer is the caller's own `USERPRINCIPALNAME()`); else the query runs under their role. reference.md §2026-10-12. Read the `DetailsMessage` detail for the verbatim DAX error before guessing at a 400. |
| Row-level security in a composite model | A `tablePermission` on a dual table may read only tables of its own source group: reading an IMPORT access table fails the load ("Some security filter expressions have errors"). Make the access table dual. Role tests on Desktop's LOCAL engine: `EffectiveUserName=<UPN>` is refused ("The name provided is not a properly formed account name") - evaluate the role predicate in DAX with the user as a literal. reference.md §2026-09-26. |
