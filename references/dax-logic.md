# DAX logic and numbers

Selections, comparisons, allocations, currency conversion, quantity fields and calculated-column cost. Rows moved verbatim from the v1 SKILL.md quick reference in v2.0.0; `§` references point to [reference.md](../reference.md). Where a row disagrees with the core, the row wins.

The core's DAX guidelines and DAX performance guide apply; these rows are traps met in real models.

| Situation | Rule |
|---|---|
| "Nothing picked" on a slicer dimension that a hidden not-blank filter keeps filtered | `ISFILTERED` is always true there: test `ISEMPTY(EXCEPT(ALLNOBLANKROW(dim[key]), VALUES(dim[key])))`. An input with no grain on that dimension counts only while it holds; sort-by names must stay unique. reference.md §2026-11-18 round 24. |
| Inlined per-row logic recalcs forever | A calc column doing per-row FILTER(bigTable) × inner CALCULATE per iterated row is pathological — hoist the inner lookup to a calc column on the ITERATED table (relationship-filtered O(n) scan), then aggregate that. |
| "Version selector broken" (all deltas zero) | Data may simply be flat: sweep per-snapshot sums FIRST, then emulate the slicers end-to-end with TREATAS inside CALCULATETABLE. Zero delta with working machinery is a data fact, not a bug. |
| Period-over-period comparison asks | Gate everything through ONE hidden date measure returning BLANK unless the selection is a single whole (edge-clipped) period — every consumer, and even footnote wording, blanks in lockstep. Fact-bounded calendars clip whole-period selections at the data edge; accept bounds equal to global MIN/MAX via `ALL('Calendar')` and anchor shifted windows at the period start. |
| "PBI shows wrong item split vs the ERP document" | EVALUATE the loaded rows for that document key FIRST — table visuals sum identical duplicate rows into one, so a screenshot lies about grain. Then audit any per-(doc, line) latest-version dedup in the feed: a renumbered/dropped line yields ghost + duplicated content with plausible totals. Dedup at document grain. No ADOMD DLL? `System.Data.OleDb` + `Provider=MSOLAP` works. Details: reference.md §2026-07-22 round 6. |
| About to divide by a quantity / lot-size field, or a reconstructed cost is absurd | **Profile the candidate field's VALUES on a real export first** (nulls, count of the default, count of > 1, min/median/max) and **compare against the source system's OWN computed figure** before blaming its master data. Two same-shaped fields sat side by side here: the charges quantity (0 or 1 on 99.5 % of rows) and the price/calculation quantity (> 1 on 30 %, up to 104,400) — round 1 verified only that the first EXISTED and moved the total 0.24 %; round 2 used the second and moved it −98.65 %. The ERP's own unit cost (0.36 vs a reconstructed 250) proved the defect was in the reconstruction, not the data. Write the rule as `fieldA > default → fieldB > default → exclude + warn`, never `else <default>` — an "accept 1 when fixed charges > 0" clause let 61.8 % of the defect through. reference.md §2026-09-06. |
| "Which date drives the FX conversion?" | Four attachment points, grep them all before answering: the source-rate derivation in the header M (an explicit rate-date column; an ERP fixed rate may be kept as one leg), the line table's M join key (currency + date), every `LOOKUPVALUE(FX…` calculated column (consolidated sales + cost components), and every display-currency measure. They CAN disagree (two surcharge measures used the reporting date while everything else used the document date). A date change must move all four through ONE date column expanded into the fact. Quantify first with a read-only headless probe on every population the rule touches — here the invoice-date rule moved totals +0.2 % / subsidiary-months ±3 %, while the naive "reporting date" variant pushed OPEN orders onto projected rates (−4.7 %, 68 lines with no rate). reference.md §2026-09-08. |
| One entity amount spread over child rows by several measures | Divide by the count of the UNION of children those measures iterate; per-measure counts add the entity amount once per measure. Prove with Σ measures = Σ entity amounts. |
| A budget or target line shows under two parents in a matrix (one parent's subtotal inflated, grand total right) | The fact joins the dimension on a NON-KEY attribute through a bridge, and that value sits under two parent paths (legacy vs ERP master data). Sweep: count `SUMMARIZE(dim, Parent1, Parent2)` paths per attribute value; > 1 = exposed. A per-cell "only where actuals exist" guard hides the duplicate but makes months stop adding up to the year and hides budget lines with no actuals: measure both before shipping it. The side-effect-free fix: a static home path per value from the CURRENT master-data source, applied to the fact as (BU, value) pairs with `TREATAS` (totals and months exact, faster than the guard). Accept it with four rule-blind checks (totals, months, parent = sum of children, zero rows) calibrated on the bad rules. reference.md §2026-10-08 rounds 1-3. |
| Same amount on several rows of a table visual | The measure is at entity grain (customer x country) but the rows group by account attributes through a bidirectional relationship. Put the attributes on the entity table as lists of distinct values and rebind the grouping; prove rows = cases and rows sum to the total. reference.md §2026-10-20. |
